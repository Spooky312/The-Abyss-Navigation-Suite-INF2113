\section{BC Methodology Application}
\label{sec:bc}

\subsection{Breakdown Activity}

Our primary objective during the Breakdown Activity was to systematically identify ambiguous, conflicting, or missing software requirements in the client's Project Specification to prepare for targeted clarification sessions. We applied our proprietary Incongruous Requirements Checklist (IRC) to 57 PS clauses, focusing on four critical validation lenses essential for project success.

The validation process encompassed ambiguity detection for subjective terms requiring client quantification, testability validation for requirements lacking clear verification methods, consistency checking across PS sections to identify conflicting requirements, and completeness verification against deep-sea software operational standards based on our industry experience.

In preparation for client discussions, we created an initial Software Context Diagram based on PS scope descriptions. This visual tool served to confirm software system boundaries and external hardware interfaces. Our preparation included specific questions for client stakeholders: "Does this diagram accurately show software interactions with all hardware systems? Are we missing any critical hardware interfaces?" The diagram revealed three potentially missing hardware interfaces that required clarification with client stakeholders.

Our findings documented for client review identified 15 software incongruities (26.3\% rate) requiring direct client input for resolution. The table below summarizes our key clarification questions prepared for the client session:

\subsection{Clarify Activity}

The Clarify Activity objective centered on engaging directly with client stakeholders to resolve identified software incongruities using visual models as collaborative discussion tools. Our Account Manager Muhammad Ridwan Putra Jasni scheduled and led the session with Triton Deepwater's Operations Team on February 21.

During the session, we presented a Use Case Diagram from the Project Specification illustrating key software system interactions. Our opening question framed the discussion: "These are the main software operational scenarios identified in your PS - are we capturing all critical software use cases for deep-sea operations?" Mission Operations Manager Sarah Whitman reviewed the use cases and provided valuable operational context.

Our key questions during the session focused on critical operational parameters. For autonomous mission execution, we needed to understand what specific accuracy level constitutes success in deep-sea navigation. Regarding hardware integration, we sought clarification on which sensor interface protocols to implement based on existing systems. For emergency handling, we required quantitative definitions of appropriate response measures.

The client provided clear, actionable answers: 99\% waypoint accuracy represents their minimum acceptable standard, ROS2 interfaces are preferred for sensor integration, and critical pressure deviations require detection within 5 seconds with response within 10 seconds. We documented these clarifications and updated our understanding of software operational requirements accordingly.

During software integration discussions, several important clarifications emerged. The client confirmed that all hardware will provide standard API interfaces for software integration. We agreed on unified JSON data format for all hardware data and determined that software will communicate with hardware via standard TCP/IP and UDP protocols. Additionally, our software architecture will include a hardware adaptation layer to handle different hardware specifications.

Our observations from client engagement revealed significant benefits from using visual models. We experienced a 40\% reduction in clarification time compared to text-only discussions, with the Use Case Diagram effectively bridging terminology gaps between client operational language and our technical understanding. Stakeholders participated more actively when discussing visual representations, leading to concrete clarifications that would have otherwise required multiple meetings.

Overall, we achieved resolution of 86.7\% (13/15) of software incongruities with direct client input and documented approval.

\section{Incongruous Requirements Checklist (IRC)}
\label{sec:irc}

We developed a project-specific software checklist based on our deep-sea domain expertise and the unique challenges identified in Triton Deepwater's Project Specification. The Brigman IRC Checklist Implementation includes:

\begin{itemize}[leftmargin=*]
\item \textbf{IRC-001 Ambiguity Detection:} Flag subjective terms needing client quantification
\item \textbf{IRC-002 Testability Validation:} Ensure each software requirement has clear verification method
\item \textbf{IRC-003 Consistency Checking:} Identify software requirement conflicts across PS sections
\item \textbf{IRC-004 Completeness Verification:} Gap analysis against software engineering standards
\item \textbf{IRC-005 Quantification:} Transform constraints into measurable parameters
\item \textbf{IRC-006 Hardware Interface Verification:} Verify all hardware interfaces are defined
\item \textbf{IRC-007 Safety Protocol Validation:} Validate emergency protocols are testable
\item \textbf{IRC-008 Data Management:} Ensure logging and retention requirements specified
\item \textbf{IRC-009 Communication Specifications:} Confirm bandwidth/latency specifications
\item \textbf{IRC-010 Autonomy Parameters:} Validate mission execution parameters
\end{itemize}

\subsubsection*{Brigman Check Categories with Client Examples}

\textbf{1. Ambiguity Detection (Our Most Frequent Finding)}

Our ambiguity detection check focuses on identifying software requirements containing subjective terms requiring client clarification. A representative client example emerged in Section 7.3 with the term "secure communication." We flagged this during our clarification session, leading the client to specify AES-256 encryption for all telemetry data.

\textbf{2. Testability Validation (Critical for Project Success)}

Testability validation ensures we can verify each software requirement through testing or inspection. When encountering the requirement "System shall be reliable" in multiple sections, we requested the client to define reliability metrics. The resolution specified that the system shall maintain 99.9\% uptime with MTBF >1000 hours.

\textbf{3. Consistency Checking (Preventing Implementation Conflicts)}

Consistency checking identifies conflicts across different PS sections. We discovered different emergency thresholds in Sections 6.4 and 7.4, presented this conflict to the operations team, and achieved resolution through unification to a single specification with escalation thresholds.

\textbf{4. Hardware Interface Completeness Verification (Applying Our Integration Expertise)}

Hardware interface verification ensures all necessary hardware interface requirements are present. Noting missing sensor interface protocols in Section 2.1, we added recommendations based on our experience with deep-sea sensor integration. The client approved our proposed ROS2-based interface specifications.

\subsubsection*{Brigman Quantitative Results}

Our analysis produced the following quantitative outcomes:
\begin{itemize}
\item Total software requirements analyzed: 57
\item Software incongruities identified: 15 (26.3\%)
\item Resolved with client input: 13 (86.7\% resolution rate)
\item Critical findings requiring immediate attention: 2 (13.3\% of incongruities)
\end{itemize}

The value demonstrated through our IRC process is significant. By identifying critical software ambiguities early, we prevent potential rework costs estimated at \$350K+ and substantially reduce project risk.

\section{Risk Analysis \& Mitigation}
\label{sec:risks}

As the software implementation vendor, we have identified and proactively addressed risks that could impact project success, budget, or schedule. Our risk assessment encompasses both technical implementation risks and project management considerations.

\subsection{Critical Software Technical Risks (Brigman Implementation Focus)}

\textbf{Risk 1: Communication Specification Ambiguity}

The Project Specification lacked quantitative bandwidth/latency specifications needed for software planning. This ambiguity creates a high-severity risk where system failure under actual conditions could lead to costly rework. Based on our deep-sea project experience, this scenario is probable (72\% likelihood). We mitigated this risk through clarification sessions that established specific requirements of 1kbps bandwidth with 30-second latency, validated against our acoustic communication models.

\textbf{Risk 2: Hardware Interface Compatibility Issues}

Customer-specified hardware may use incompatible interface protocols, requiring additional adaptation layer development with medium-high severity impact. Given hardware specification diversity, this risk presents moderate likelihood (55\%). Our mitigation strategy proposes standardized middleware interfaces and adapter patterns, with validation through a flexible hardware abstraction layer in our software architecture.

\textbf{Risk 3: Sensor Integration Complexity}

Hardware sensors may lack interface specifications needed for our integration, potentially causing integration delays with high severity impact. Based on sensor specification review, this scenario is very probable (85\% likelihood). We mitigated this by proposing and gaining client approval for ROS2 interface standards, with the integration approach documented for the next phase.

\subsection{Project Management Risks (Brigman Delivery Focus)}

\textbf{Risk 4: Scope Creep Post-Clarification}

Client clarification may introduce new software requirements impacting budget and schedule. We address this through a formal change control process with requirement traceability, ensuring all new software requirements undergo impact analysis before acceptance.

\textbf{Risk 5: Hardware Specification Changes}

The client may change hardware specifications during software development. Our mitigation includes defining a hardware specification freeze date in the contract, with hardware changes requiring formal change requests and impact assessments.

\subsection{Brigman Software Integration Risk Mitigation Strategy}

Our comprehensive risk mitigation strategy employs multiple approaches. We have adopted flexible architecture design with modular components for easy adaptation to hardware changes. Early hardware simulation enables software testing before hardware availability through created simulators. A hardware abstraction layer implementation isolates hardware-specific code, while continuous integration establishes a CI/CD pipeline for rapid adaptation to hardware changes.

Our proactive risk identification and mitigation approach reduces project uncertainty and provides clear visibility into potential challenges, demonstrating Brigman's risk management value throughout the project lifecycle.
